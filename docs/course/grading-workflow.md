# Grading Workflow (instructor)

How a lab goes from twelve submitted archives to a column in the gradebook.

The rubric itself — what the ten points are for — is in [Grading & Rubrics](grading.md). This page
is the mechanics.

> [!NOTE]
> **Student IDs on this page are fabricated**
>
> `2026000001` and friends are illustrative. This repository is public, so no real 학번 appears
> here, and the files that do contain them — `course/roster-*.txt` and `course/scores-*.tsv` — are
> git-ignored.

---

## What is decided by whom

| | Points | Decided by |
|---|---:|---|
| Correctness | 4 | `lab.sh check`, automatically |
| Reproducibility | 1 | `lab.sh check`, automatically |
| **Evidence** | **3** | **You, reading the report** |
| **Understanding** | **2** | **You, reading the report** |

Half the rubric is machine-checked and it is not the interesting half. See
[how the two human scores are decided](grading.md#how-the-two-human-scores-are-decided).

> [!NOTE]
> **`grade` and `scores` need a clone, not the student bundle**
>
> They live in `scripts/lab_grading.py`, which `export_student_bundle.sh` does not copy — the
> roster reader, the late-penalty table and where marks are stored are not a student's to run.
> Everything else (`new`, `check`, `submit`, `selftest`) works in either place. Run `grade` from
> your clone of the course repository; in a bundle it says so in one line.

## The loop

### 1. Collect

```bash
cd ~/mrider
bash scripts/lab.sh grade 1 --zips ~/Downloads/lab1
```

**Grade the archive, not the branch.** The LMS upload is the authoritative submission, so `--zips`
checks the artefact that actually counts. The archive is cut from the commit with `git archive`, so
it agrees with the branch unless someone has gone out of their way.

`--roster course/roster-2026-fall.txt` runs identical checks against git instead. It is the faster
read when you only want to see who is stuck, and the only option before the LMS deadline passes.

Output is one file per student:

```
dist/grade/lab1/2026000001.md
```

containing the submission's provenance header, the automated verdict, and a reminder of what only
you can judge.

### 2. Open the marks file

```bash
bash scripts/lab.sh scores 1
# created course/scores-2026-fall-lab1.tsv with 12 students
```

```
# uniqname	auto	evidence	understanding	late	note
2026000001	5	.	.	0	
2026000002	5	.	.	0	
2026000003	0	.	.	0	
```

`auto` is correctness + reproducibility, seeded from the automated checks — **a suggestion, not a
verdict.** Edit it if you disagree. A `0` means the checks failed or nothing was submitted.

`late` is whole days past the due date, **read from the LMS timestamp**, not the commit.

### 3. Read, and fill in

Open each `dist/grade/lab1/<uniqname>.md`, read the report it points at, and put numbers in the
`evidence` (0–3) and `understanding` (0–2) columns. A dot means *not yet read*, so you can stop
halfway and resume.

### 4. Total and export

```bash
bash scripts/lab.sh scores 1
```

```
uniqname     auto  ev  und  late  raw  final
----------------------------------------------
2026000001      5   3    2     0   10   10.0
2026000002      5   2    1     2    8    6.4  <- late
2026000003      0   0    0     0    0    0.0
----------------------------------------------
mean                                     5.5

9 not yet marked: 2026000004, 2026000005, ...

LMS upload: dist/grade/lab1/final.csv
```

Re-running never overwrites your marks and always lists who is still pending. The late policy
(−10%/day, floor 50%, zero after seven days) is applied for you.

`final.csv` is `uniqname,raw,late_days,final` — the shape a gradebook import wants.

## Where a mark lives

> [!WARNING]
> **`course/scores-<term>-lab<N>.tsv`, and nowhere else**
>
> `dist/grade/lab1/<uniqname>.md` is **regenerated by every `grade` run**, and `dist/` is
> git-ignored. A number typed there is lost twice over — once when you re-run, once when you clone
> somewhere else.
>
> The marks file is git-ignored too, deliberately: it is student grade data and this repository is
> public. **Back it up somewhere that is not this repository.**

## Adding a student mid-term

Append to `course/roster-2026-fall.txt` and re-run. The script is idempotent — it creates nothing
that already exists, and re-asserts every collaborator.

```bash
bash scripts/provision_labs.sh --dry-run    # read the account-name column
bash scripts/provision_labs.sh              # creates the repo AND sends the invitation
bash scripts/provision_labs.sh --status     # confirm it is pending, then accepted
```

There is no separate "send invitation" step: the collaborator call *is* the invitation, and GitHub
delivers it by email and on the notifications page.

> [!NOTE]
> **Re-running also turns GitHub Actions off**
>
> `submit` pushes the student's whole tree, including this project's
> `.github/workflows/`. Those then run in *their* repository: the `docs` workflow builds the course
> site and fails deploying it to GitHub Pages, which is not enabled there.
>
> The student sees a red ✗ on their repository the moment they submit. One of them read that as a
> failed submission and spent a morning fixing Pages permissions in a repository where Pages was
> never meant to run — while their work had uploaded correctly the whole time.
>
> `provision_labs.sh` switches Actions off on every repository it touches. **Editing the script is
> not retroactive** — run it once after any change, and `--status` flags anything still outstanding.

> [!CAUTION]
> **End the roster with a newline**
>
> A final line with no trailing newline used to be read and then silently discarded, because
> `read` returns non-zero at EOF. The student got no repository and no invitation, and nothing said
> so — the row simply was not there.
>
> Fixed in `provision_labs.sh`, but the habit is worth keeping: after editing the roster, check the
> count.
>
> **Count it with a pipe, not with `grep -c`.** `grep -c` **undercounts by one** when the file
> lacks a trailing newline — the very condition this box exists to catch. On 2026-10-01 a complete
> 13-student roster counted as 12 this way. Piping through `wc -l` is correct, because grep
> terminates every line it emits.
>
> ```bash
> grep -vE '^\s*#|^\s*$' course/roster-2026-fall.txt | wc -l
> ```

## Peer evaluation

Twice: Week 12 (a check, no grade effect) and Week 14 (adjusts the Team deliverable, up to ±15%).
The rule the students were given is in [Teams & Tracks](teams.md#peer-evaluation).

### The form

**One Google Form per team**, filled in during the last 15 minutes of class. Collect it in the room:
a form sent home comes back from eight of thirteen. Set it to one response per person and do not
show respondents the results.

Every question that names a member uses **the same label for that member**, character for
character. The script identifies a self-rating by that label and nothing else.

| # | Question | Type |
|---|---|---|
| 1 | **Who are you?** | Dropdown: one choice per member |
| 2 | **Contribution** — did they deliver what they owned? Rate every member, yourself included. 1 = almost nothing, 3 = what was agreed, 5 = well beyond it | Multiple-choice grid: rows = members, columns = 1 2 3 4 5, one response per row required |
| 3 | **Reliability** — could the team depend on their commitments? 1 = rarely, 3 = usually, 5 = always | Same grid |
| 4 | **Collaboration** — did they make the team work better? 1 = made it harder, 3 = neutral, 5 = clearly better | Same grid |
| 5 | **What did this person do that the git history would not show me? [member]** — one question per member, the member's label in square brackets at the end | Paragraph, optional |
| 6 | **Is there anything about how the team is working that I should know?** | Paragraph, optional |

Form description, shown at the top:

> Confidential: only the instructor reads individual responses. Rate what you observed, not what
> you assume. Your own row is not counted in your score. The Week 12 evaluation changes no grade.

A grid question exports one column per row, named `Contribution [<member>]`, which is the shape the
script expects. Question 5 is written with the bracket by hand so that it exports the same way.

### Reading it

*Responses → ⋮ → Download responses (.csv)*, one file per team, then:

```bash
python3 scripts/peer_eval.py ~/Downloads/peer1-team1.csv --text
```

```
4 of 4 members responded; team mean of received scores = 3.67

member                    recv  n  self  ratio  mult  flags
------------------------------------------------------------------------
Member A                  4.33  3  5.00   1.18  1.15
Member B                  4.00  3  4.00   1.09  1.00
Member C                  4.00  3  4.00   1.09  1.00
Member D                  2.33  3  5.00   0.64  0.85  received < 3; ratio < 0.8; self is 2.7 above received
```

`recv` is the mean from the other members, `n` how many of them rated this person, `ratio` is `recv`
over the team mean, and `mult` is the multiplier the published rule gives. The flags are where to
look first; `--text` prints what was written about each member underneath.

At **Week 12** nothing is applied. A flag is a reason to talk to the team that week.

At **Week 14** the multiplier applies to that student's Team deliverable score, after it has been
read against the free text, the fork's commit history and the standup notes. With three or four
raters, one person marking a teammate down moves the mean a long way: the `raters disagree` flag
names who, and the free text has to carry the reason.

> [!WARNING]
> **The output is grade data and it is printed, not saved**
>
> Keep the CSVs outside this repository. Record the ratio and the multiplier you used in
> `course/records-<term>-merges.md`, which is git-ignored.

## Team rubrics and the course total

The three team components are marked per team, and two things are marked per student. All of it
lives beside the lab marks, in the same git-ignored pattern:

| File in `course/` | One row per | Columns |
|---|---|---|
| `scores-<term>-mid.tsv` | team | demonstrated 30, evidence 25, interface 20, risk 15, delivery 10 |
| `scores-<term>-deliverable.tsv` | team | functionality 30, evidence 25, quality 20, integration 15, failure 10 |
| `scores-<term>-final.tsv` | team | autonomous 25, depth 20, failure 20, reproducibility 15, safety 10, presentation 10 |
| `scores-<term>-students.tsv` | student | team, track, peer multiplier, participation 0–10 |

The columns are the rubric rows in [Grading & Rubrics](grading.md), in the same order.

```bash
python3 scripts/course_grade.py --init     # once: creates the four files, all dots
python3 scripts/course_grade.py            # the table, as far as it is marked
python3 scripts/course_grade.py --csv dist/grade/course.csv
```

`--init` never overwrites a file that exists. The student list comes from the first lab marks file.

```
uniqname     team trk  labs   mid  deliv  mult final  part  total   of    pct
-----------------------------------------------------------------------------
student_a       1   W  30.0  13.5      -  1.00     -     -   43.5   45  96.7%
student_b       2   E  24.6  11.2      -  1.00     -     -   35.8   45  79.6%

Not fully marked: deliverable, final, participation. "of" is the weight each total is out of.
```

A dot means *not marked yet*. A component with a dot is left out of the total **and** out of the
weight the total is measured against, so the table can be read in Week 12 without a missing final
demo looking like a zero.

**The peer multiplier is typed in by hand.** `peer_eval.py` prints a suggestion; it goes into the
`peer_mult` column only after it has been read against the free text and the commits. It multiplies
the Team deliverable and nothing else, and the result is limited to the full 25%: a multiplier
above 1.00 can recover points a team lost, not exceed the component.

## Things the LMS does to your downloads

**It renames them.** Student names get prefixed; a second copy of the same file gets `-1` appended.
Identity is therefore read from the **`Uniqname` row inside the report**, not from the filename, so
neither invents a student nor splits one in two.

**It gives you duplicates.** Two archives claiming the same uniqname are collapsed, last one
winning — which is also the right answer for a resubmission. The run prints a note when it happens.
