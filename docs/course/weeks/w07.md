## Lecture

### 1. Why a microcontroller at all

The laptop runs Linux, which is not a real-time operating system. It cannot promise to close a
position loop at 200 Hz — it can usually do it, which is worse than a clear no, because the failures
are rare and load-dependent.

So the split is by **timing guarantee**:

| | Runs where |
|---|---|
| Steering position loop, safety state machine, PWM generation | **Teensy 4.1** — deterministic |
| SLAM, planning, perception, logging | **Laptop** — best effort |

[ADR D3](../../design/adr-dbw-architecture-review.md) adopted a **single** Teensy 4.1, replacing a
Pixhawk 6C + Arduino Nano topology.

!!! danger "A single controller is a single point of failure — and the ADR says so"

    D3 was adopted **conditional** on a layered override that does not depend on it:

    > SBUS into the Teensy for normal closed-loop override, *plus* a hardware RC signal MUX on the
    > E-stop chain as the independent deeper fallback. **The condition is not optional; it is what
    > makes the single-point-of-failure objection answerable.**

    Note what the record does *not* do: it does not claim the objection was wrong. It names the
    objection, and buys it off with a mechanism. That is what an honest decision record looks like.

There is also a **pre-registered fallback**, E4: if the Teensy loop cannot hold ≤ 1° steady-state
with no sustained oscillation at bring-up Stage 1, adopt a motion-controller daughterboard **rather
than tuning without bound.** The trigger was written before the attempt.

### 2. micro-ROS

micro-ROS puts a genuine ROS 2 node on the microcontroller. The Teensy publishes and subscribes real
typed topics; an **agent** process on the laptop bridges them onto the DDS network.

```
Teensy 4.1                          Laptop
┌──────────────────┐                ┌────────────────────────────┐
│ micro-ROS node   │  USB serial    │ micro_ros_agent            │
│  sub DbwCommand  │◀──────────────▶│   ▲                        │
│  pub DbwStatus   │                │   ▼                        │
│  200 Hz loop     │                │ /mitt/dbw/{command,status} │
│  safety FSM      │                │   ▲                        │
└──────────────────┘                │   ▼  mitt_hardware plugin  │
                                    │    controller_manager       │
                                    └────────────────────────────┘
```

**ADR-SW1 — one transport, one clock, typed messages.** Both directions on the same link, stamped on
the same clock. As `DbwStatus.msg` puts it: *a single `ros2 topic echo` therefore shows both sides of
the control loop.*

That is not a convenience. Debugging a control loop whose command and feedback arrive over different
transports on different clocks is a category of pain this design simply refuses to enter.

!!! info "`micro_ros_agent` is not in the Humble apt repositories"

    Build it from source **now**, during track work — not in Week 13 when it blocks the vehicle.
    [Build guide §5.4](../../build/05-software.md) has the procedure. Record the commit you built.

### 3. The interface contract

Read both files in `mitt_msgs/msg/`. They are short and every line is deliberate.

**`DbwCommand`** — laptop → Teensy, ≥ 50 Hz:

- `steering_angle` — **radians**, clamped by firmware to ±0.3927 (±22.5°)
- `speed` — signed m/s, positive forward

**`DbwStatus`** — Teensy → laptop, ≥ 50 Hz:

- `steering_angle` — **measured**, from the load-side sensor. *"Authoritative — never derived from
  the motor encoder, which sits upstream of the gearbox backlash."*
- `steering_setpoint` — the setpoint currently being tracked, **echoed back**
- `wheel_speed`, `drive_ticks` — *"PPR is a MEASURED constant… do NOT assume 52"*
- `mode` — ESTOP / MANUAL_RC / AUTONOMOUS
- `faults` — a bitfield

!!! success "Three design choices in there worth stealing"

    **Echoing the setpoint back.** The firmware already knows it — but now commanded and measured
    sit on **one time axis in one bag**, and "did it not follow, or did it not receive?" becomes a
    question you can answer from a single recording rather than by correlating two logs.

    **Radians in the message, degrees never.** One unit crosses the boundary. Unit confusion at an
    interface is a classic and expensive bug.

    **A fault bitfield, not a boolean.** Six named causes — `ENCODER`, `SETPOINT_STALE`, `AT_LIMIT`,
    `STALL`, `RC_LOSS`, `OVER_CURRENT` — and several can be set at once. `is_faulted: true` tells you
    to stop. This tells you *why*, which is what you need at 2 a.m. with the vehicle on blocks.

### 4. The timing contract

| | |
|---|---|
| `DbwCommand` publish rate | ≥ 50 Hz |
| `DbwStatus` publish rate | ≥ 50 Hz |
| Steering position loop | ≥ 200 Hz on the Teensy |
| Command staleness → ESTOP | > 500 ms |
| Joystick → wheel latency | ≤ 100 ms at p95 |
| USB dropouts | **zero** over ≥ 30 minutes |

These are **acceptance gates**, not aspirations. The Electrical track is graded against them, and
`FAULT_SETPOINT_STALE` exists to make the 500 ms rule observable rather than merely intended.

### 5. `hardware_interface` — the other side

`ros2_control` talks to hardware through a plugin implementing a fixed cycle:

```cpp
return_type read(const rclcpp::Time&, const rclcpp::Duration&) override;
// hardware state -> state_interfaces
return_type write(const rclcpp::Time&, const rclcpp::Duration&) override;
// command_interfaces -> hardware
```

For MRider, `read()` takes the latest `DbwStatus` and fills the joint state interfaces; `write()`
takes the controller's commands and publishes a `DbwCommand`.

!!! danger "There was never working code here to reuse"

    B-MROVER's `carlikebot_system.cpp` is an **unmodified upstream demo stub** — `read()` echoes the
    command back as state, `write()` only logs ([finding F3](../../design/software.md)).

    A stub that echoes commands back as state is the worst possible thing to inherit: in simulation
    and in any test that does not touch hardware, it looks like it works perfectly.

    `mitt_hardware` is **new work**, and it is the Software track's keystone. Merge 3 in Week 13
    exists to prove ADR-SW4 with it: the identical teleop launch running in sim and on hardware,
    differing only in this plugin.
