### The acceptance gates

From [software.md §8](../../design/software.md#8-semester-1-scope-and-software-acceptance-gates).
For each one, your fork's `docs/build/` records the number, how it was measured, and the conditions.
"Not measured, because …" is an entry. A blank is not.

| Gate | Target |
|---|---|
| `colcon build && colcon test` | Clean; the tests assert something that is not a linter |
| `/mitt/dbw/status` rate | **≥ 50 Hz**; zero USB session dropouts over **≥ 30 min** |
| Joystick to wheel-motion latency | **≤ 100 ms** at p95 |
| Same launch in sim and on hardware | Differs only in the plugin (shown at Merge 3) |
| Twin against vehicle | Steering range, rate limit, wheelbase, command latency within **10%** |
| Odometry | Drift **≤ 2%** over 20 m straight; heading error **≤ 5°** after a closed 20 m figure-8 |
| SLAM | Closes a **≥ 30 m** loop; the same wall agrees within **≤ 10 cm**; the map loads in Nav2 unedited |

> [!NOTE]
> **Missing a gate is a result**
>
> These targets were written before any of this hardware existed. A measured 4% odometry drift with
> a diagnosis (tyre deflection under load, a wheel radius measured unloaded) is a finding, and it is
> what the next cohort starts from. An unmeasured gate tells them nothing.

## Lecture

### 1. A gate is a number, a procedure and a condition

"Odometry drift is under 2%" is not checkable. This is (the numbers are made up for the example):

> Drift 1.6% of distance (0.32 m over 20.0 m), mean of five runs, range 1.1–2.3%. Straight line
> along the corridor, tape-measured end points, 0.4 m/s, vehicle 2 with its measured overlay at
> fork commit `abc1234`, battery 12.6 V at the start. Bags in `bench/odom_2026-12-12/`.

Five things make it a claim someone else can test: the number **with its spread**, the number of
trials, the procedure, the conditions, and where the raw data is. One run is an anecdote. And note
that this example **fails the gate on one of its five runs**, and says so.

### 2. How to write a failure analysis

The final demo gives failure analysis 20 points and the team deliverable another 10. It is the
part of the report that cannot be produced the night before, because it needs evidence collected
when the failure happened.

For each significant failure, five lines:

| | |
|---|---|
| **Observed** | What happened, in terms of what a sensor or a log showed. Not "it crashed" |
| **Subsystem** | Which track's part was responsible |
| **Evidence** | What localised it there: the bag, the plot, the log line, the experiment that ruled the others out |
| **Change** | What you did about it |
| **Outcome** | Whether that worked, with the number before and after. "Not fixed" is an outcome |

> [!TIP]
> **The repository has three worked examples**
>
> [software.md §4.5–4.7](../../design/software.md) records a planner swap, a recovery behaviour
> that was tried and left out, and a planner that put a front corner through a post. The second
> one drew a conclusion that turned out to be **wrong**, and it is kept on the page with its
> correction. That is the form: what was believed, what the evidence showed, what changed.

The most common weak analysis names a cause without ruling out the others. "The map was bad because
of odometry" is a guess until you have shown it was not the extrinsics, the clock or the scan
plane. [Week 11's table](w11.md#5-reading-a-bad-map) is a list of what to rule out.

### 3. Reproducibility is tested by someone else

*Could another team rebuild this from what you wrote down?* is 15 points, and there is one honest
way to find out: hand your README to a teammate from another track and watch them follow it without
helping.

What they will need, and what is usually missing:

- the fork commit and the firmware commit the result was measured at
- `config/vehicles/vehicle<n>.yaml` and the calibration files, committed
- the exact commands, with `vehicle:=<n>` and `use_sim_time:=false` written out
- the saved map, and how the vehicle was placed on it
- anything set by hand on one laptop: a udev rule, an exported variable, a parameter changed in a
  terminal and never written to a file

> [!WARNING]
> **A parameter you changed in a terminal is not in your repository**
>
> `ros2 param set` lasts until the node restarts. If your working configuration came from one, the
> file in your fork describes a vehicle that does not work, and nobody will know until the demo.
> Before you leave today: restart the stack from a clean terminal and confirm it still behaves.

### 4. The architecture, once, as a whole

You have each worked in one part of this for eight weeks. Trace one command through all of it,
out loud, as a team:

```
joystick or Nav2 ─▶ twist_mux ─▶ ackermann controller ─▶ mitt_hardware ─▶ micro-ROS agent
                                                                              │ USB
   EKF ◀─ odometry node ◀─ DbwStatus ◀──────────────────────────────── Teensy firmware
    │                                                                         │
    ▼                                                              motor driver, relay MUX
 SLAM / AMCL ─▶ Nav2                                                 RC receiver, E-stop
```

Every arrow is an interface one track gave another. At the demo you will be asked about an arrow
that is not yours.
