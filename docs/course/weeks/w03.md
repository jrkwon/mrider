## Lecture

### 1. Four ways to talk

| Mechanism | Shape | Use when |
|---|---|---|
| **Topic** | one-way, many-to-many, continuous | Streaming data: sensors, commands, state |
| **Service** | request/response, blocking, fast | A discrete question or action that returns quickly |
| **Action** | request/feedback/result, cancellable, long | Something that takes time and might be aborted |
| **Parameter** | named, typed, node-scoped configuration | A value that tunes behaviour, readable and settable at runtime |

The common mistakes are worth naming:

- **A service for streaming data.** Round-trip per sample; you will not make rate.
- **A topic for something needing acknowledgement.** Publishing is fire-and-forget. You will not know
  whether anyone acted on it — or whether anyone was even listening.
- **A service for something slow.** It blocks and cannot be cancelled. That is what actions are for.

!!! info "Nav2 uses all four, and you have already met them"

    `navigate_to_pose` is an **action** — it takes minutes and you must be able to cancel it.
    `/goal_pose` is a **topic**. Costmap parameters are **parameters**. Lifecycle transitions are
    **services**.

    A footnote from the project's own runbook that will save you time later: sending a goal with
    `ros2 topic pub --once /goal_pose` **silently drops it**. The publisher exits before discovery
    completes, so nobody ever receives the message. Use `-r 2` under a `timeout`. Another silent
    failure, and this one is written down because it cost someone real time.

### 2. Parameters

```python
self.declare_parameter('max_speed', 0.5)
value = self.get_parameter('max_speed').value
```

```bash
ros2 param list /governor
ros2 param get  /governor max_speed
ros2 param set  /governor max_speed 1.5
```

Parameters are **live state**, not startup configuration. Everything in
`mitt_controllers.yaml` and `nav2_params.yaml` arrives this way, which is why you can retune a
planner without restarting it — and why a parameter set from a stray terminal can change your
vehicle's behaviour without anything being logged.

### 3. QoS — the silent one

Every publisher and subscriber carries a Quality of Service profile. **If the profiles are
incompatible, they do not connect, and nothing says so.**

| Policy | Options | Meaning |
|---|---|---|
| **Reliability** | `RELIABLE` / `BEST_EFFORT` | Retransmit until delivered, or send once |
| **Durability** | `TRANSIENT_LOCAL` / `VOLATILE` | Late joiners get the last message, or they do not |
| **History** | `KEEP_LAST(n)` / `KEEP_ALL` | Buffer depth |

**The compatibility rule is asymmetric.** A `RELIABLE` publisher satisfies a `BEST_EFFORT`
subscriber — reliable delivery is a stronger promise than best-effort demands. The reverse fails: a
`BEST_EFFORT` publisher cannot satisfy a subscriber demanding reliability, and they simply never
connect.

Conventionally: sensor streams are best-effort (a dropped scan beats a late one), commands and state
are reliable, and `/robot_description` is `TRANSIENT_LOCAL` so a node starting late still receives it.

### 4. Arbitration, and what it is not

`twist_mux` decides which software source reaches the controller. Joystick 100, navigation 10.

**It is not the safety system.** From the file's own header comment:

> On the REAL vehicle this is NOT the safety authority. Authority there is electrical and layered:
> hardware E-stop, relay MUX to STOCK, hardware RC signal MUX, then SBUS override — three of which
> work with the controller firmware dead.

Sit with that. A software mux protects you from a *misbehaving software source*. It cannot protect
you from the software itself dying, from the computer freezing, or from the USB cable falling out. In
each of those cases the mux is gone too.

The four real layers, in order of how much they depend on software:

| Layer | Works if the firmware has crashed? |
|---|---|
| Hardware E-stop — cuts traction power | **Yes** |
| Relay MUX — reverts to stock mechanical steering | **Yes** |
| Hardware RC signal MUX | **Yes** |
| SBUS override into the controller | No |

!!! danger "The engineering principle, which is bigger than this vehicle"

    A safety mechanism that shares a failure mode with the thing it protects against is not a safety
    mechanism.

    Lab 3 has you build a speed governor — a piece of software that limits the vehicle's speed, with
    a network service that can switch it off, no authentication, and no behaviour at all if its
    process dies. Building it is useful. Being able to say precisely why it must never be *relied*
    on is the actual learning objective.

### 5. Three silent failures, and counting

| Week | Failure | How it announces itself |
|---|---|---|
| 1 | `ROS_DOMAIN_ID` mismatch | Exit 0, empty stderr, 2 topics instead of 21 |
| 3 | QoS incompatibility | Nothing whatsoever |
| 4 | Wrong sensor extrinsic | Everything runs; the output is quietly wrong |

Week 4 adds the worst kind: the one where every component is healthy and the *system* is wrong.
