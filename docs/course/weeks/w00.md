## 1. What this course is

Most robotics courses teach middleware on a simulator, using exercises invented for the course. This
one does not. **You will learn ROS 2 by finishing a real vehicle.**

[MRider](../../index.md) is a 12 V ride-on car being converted into a drive-by-wire autonomous
platform. Its digital twin already drives, maps a warehouse, and navigates to goals. And it is
unfinished in specific, named ways:

| Missing | Status today |
|---|---|
| `firmware/` | No firmware in the repository at all |
| `mitt_hardware` | The plugin that makes one launch file drive both sim and the real car |
| Measured geometry | The dimensions file says, in capitals, *"NOTHING IN THIS FILE HAS BEEN MEASURED"* |
| A real test suite | 29 tests exist. All 29 are linters |

By December those exist because you built them.

**The shape of the semester:** Weeks 1–5 are individual — everyone does the same five labs, graded on
their own work, because in a team project foundational gaps hide. From Week 6 the class splits into
four teams (Electrical, Chassis, Simulation, Software), which merge one pair at a time into a working
vehicle. See [Teams & Tracks](../teams.md) and the [Syllabus](../syllabus.md).

> [!TIP]
> **The standard you are held to**
>
> *"Honest failure outscores a lucky success."*
>
> A subsystem that does not work, with a correct and evidenced diagnosis of **why**, scores above one
> that works for reasons you cannot explain. That is not generosity — it is the professional
> standard. A result you cannot explain is one you cannot reproduce, extend, or trust.

## 2. What a robot is

There is no settled definition. Three serious attempts:

> A machine — especially one programmable by a computer — capable of carrying out a complex series of
> actions automatically. *(Oxford English Dictionary)*

> An autonomous machine capable of sensing its environment, carrying out computations to make
> decisions, and performing actions in the real world. *(IEEE)*

> "I don't know how to define a robot, but I know one when I see one."
> *(Joseph Engelberger, robotics pioneer)*

The IEEE one is the most useful here, because it names the loop:

```
        ┌──────────────── environment ────────────────┐
        │            (beyond our control)             │
        ▼                                             │
     sensors  ────▶  autonomy  ────▶  actuators  ─────┘
      "see"          "think"            "do"
                 ( things we design )
```

**The split matters more than the diagram.** Everything inside the robot is something you design and
are responsible for. The environment is not. Most of the hard problems in this course live exactly at
that boundary — where a designed thing meets a world that does not cooperate.

On MRider specifically:

| | |
|---|---|
| **See** | 2D LiDAR, camera, IMU, wheel encoder, steering angle sensor |
| **Think** | SLAM, EKF, Nav2 — obstacle detection, mapping, state estimation, path planning, control |
| **Do** | Steering gearmotor, two drive motors through a motor driver |

## 3. The tools

> [!NOTE]
> **You cannot build complex systems without proper tools**
>
> This framing, and much of this section, follows Prof. Paul Robinette's *Introduction to Robotics
> and Tools* lecture for [EECE 5560 at UMass Lowell](https://sites.uml.edu/paul-robinette/teaching/eece-5560-fall-2025/5560-fall-2025-schedule/).
> It is a good sequence and there is no reason to reinvent it.

### Linux

An open-source operating system: mature, free, and what robots actually run. ROS 2 targets it
first-class, and everything in this course assumes it.

We use **Ubuntu 22.04 LTS**, natively installed. Not a VM, not WSL — see
[Environment Setup §1](../environment.md) for why, in one line: Gazebo needs a real GPU.

New to Linux? [ryanstutorials.net/linuxtutorial](https://ryanstutorials.net/linuxtutorial/) is a good
free primer. Work through it this week.

### The command line

Most robotics tooling is CLI-first. GUIs have to be explicitly written; a command line is what
developers give you for free.

The notation, which **every lab in this course uses**:

```
$ <command> [options]
```

| | |
|---|---|
| `$` | The prompt. It indicates a terminal command — you do not type it |
| `<...>` | **Required.** Replace with your own value |
| `[...]` | **Optional** |

So `$ ros2 topic echo <topic_name>` means: type `ros2 topic echo` followed by an actual topic name.

You will use **bash**. Other shells exist (zsh, tcsh) and treat scripts slightly differently; the
course assumes bash throughout.

### git

A system for tracking versions of code, and for sharing it. You will submit work through it, and
your commit history is part of your [participation grade](../grading.md#participation-documentation-10)
— not as surveillance, but because *what you did and when* is genuinely the best available record of
engineering work.

If you have never used git, learn these six before Week 2: `clone`, `status`, `add`, `commit`,
`push`, `pull`.

### Why not Docker

The reference course offers Docker as an install option, and it is a reasonable one in general —
containers package an entire configuration so it runs identically everywhere.

**This course does not use it**, and the reason is specific: you will run Gazebo, a 3D physics
simulator, for most of the semester. It needs **GPU-accelerated OpenGL**. That works acceptably in
Docker on a Linux host and badly everywhere else, and debugging GPU passthrough would cost more time
than a native install ever will.

Native Ubuntu 22.04. Dual-boot if you need to.

## 4. What middleware is for

A robot is not one program. It is a camera driver, a LiDAR driver, a localiser, a planner, a
controller, and a safety monitor — written by different people, in different languages, running at
different rates, sometimes on different machines.

They have to talk. Historically, that went badly:

> Old days: everyone wrote their own code… everyone sorted out multi-process communication on their
> own **(poorly)**.
>
> — *ROS2 Deep Dive*, EECE 5560

A **robot middleware** is the layer that solves that once, properly, for everyone. ROS 2 gives you:

- **Named, typed channels** instead of ad-hoc sockets
- **Discovery** — processes find each other without being told where anything is
- **Introspection** — list, inspect, record, and replay everything at runtime
- **Language independence** — Python and C++ nodes in one system

### What it costs you

This is the part people are not warned about, so hear it now:

> [!CAUTION]
> **Coupling that used to be a compile error is now a runtime condition**
>
> Topic names must agree. Message types must agree. QoS settings must agree. Domain IDs must agree.
>
> When they disagree, **mostly nothing happens, and nothing complains.** No error, no warning, no log
> line — just a system that looks dead while running perfectly.
>
> Lab 1 has you cause this deliberately, because recognising the *shape* of it is worth more than any
> single fact in this course.

### The graph

A ROS 2 system is a **graph**: nodes are the processes, and the edges are the channels between them.

```
   [talker] ──chatter──▶ [listener]
       │
       └────babble────▶ [logger] ◀──jabber── [sensor]
```

No node knows where the others are, or whether they exist. It publishes to a name, and anyone
listening to that name receives it. That is what makes the parts independently replaceable — and
also why a typo in a topic name produces silence rather than an error.

### Underneath: DDS

ROS 2 does not implement its own networking. It sits on **DDS** (Data Distribution Service), an
industry standard for real-time message passing, with several competing implementations.

You mostly do not need to care — except that you will meet it in Week 1, because MRider pins a
specific DDS implementation and the reason is a real bug. That is a Week 1 story.

## 5. The ROS 2 vocabulary

Names and mental models today. The labs supply the practice.

### Code

| Term | What it is |
|---|---|
| **Node** | A single program participating in the graph. One job each, by convention |
| **Package** | A unit of distribution: nodes, configs, launch files, message definitions |
| **Workspace** | A directory of packages you build together with `colcon` |

### Communication

| Term | What it is | Use when |
|---|---|---|
| **Topic** | A named, one-way, many-to-many stream | Continuous data: sensors, commands, state |
| **Message type** | The schema of what flows on a topic | Both ends must agree, exactly |
| **Service** | Request → response, blocking | A discrete question answered quickly |
| **Action** | Request → feedback → result, cancellable | Something slow that might be aborted |

### State and geometry

| Term | What it is |
|---|---|
| **Parameter** | Named, typed, per-node configuration — readable *and settable at runtime* |
| **Transform (TF)** | The relationship between coordinate frames, tracked over time |

That last one deserves a sentence, because it is the concept students most often underestimate: every
sensor reading arrives in *some* frame. The LiDAR reports distances from the LiDAR. The camera sees
from the camera. Turning any of it into "where is that obstacle relative to the car" is what TF is
for, and getting it slightly wrong produces a system where every component is healthy and the answer
is quietly wrong.

## 6. Humble, not Jazzy

ROS 2 ships a new release most years, pinned to an Ubuntu version:

| Distribution | Ubuntu | |
|---|---|---|
| **Humble Hawksbill** | 22.04 | **What this course uses** |
| Jazzy Jalisco | 24.04 | What most current tutorials assume |

We use Humble because **that is what the working MRider stack runs on** — the simulator, the
controllers, SLAM, and Nav2 have all been brought up and verified on it. Choosing the newer release
would mean porting and re-verifying a working system before the course could start.

> [!WARNING]
> **Most tutorials you find will be for Jazzy**
>
> Including the recommended textbook. Most content transfers directly, but three areas differ enough
> to waste your afternoon: the `ros_gz` package naming, the `gz_ros2_control` build, and several Nav2
> parameter names.
>
> **Where a weekly note and an external tutorial disagree, follow the weekly note.** They carry a
> *Humble note* callout wherever the difference matters.

## 7. Before Week 1

Week 1 opens with [Lab 1](../labs/lab1.md), which assumes a working machine. Getting there takes
**2–4 hours**, most of it unattended downloading.

**Do this week:**

- [ ] Read [Environment Setup](../environment.md) end to end before starting
- [ ] Install Ubuntu 22.04 LTS natively — the long step, start it first
- [ ] Install ROS 2 Humble and Gazebo Harmonic (§3–5)
- [ ] Clone the repository and build the workspace (§6–7)
- [ ] Run `bash scripts/check_env.sh` until it reports **`FAIL: 0`**
- [ ] Confirm `source ros2_ws/setup_env.sh` prints **`isolated to loopback`**
- [ ] Skim [M1](../../learn/m1-ros2-intro.md)

> [!CAUTION]
> **Start the graphics driver step early**
>
> Everything else in that list is downloading and waiting. The one step that genuinely fails is GPU
> drivers — and if `glxinfo -B` reports `llvmpipe`, Gazebo runs at about one frame per second and
> nothing in this course works.
>
> That is not fixable in five minutes on the morning of class. Check it this week.

If you are stuck for more than **30 minutes**, stop and ask. Save the terminal output and bring it.
Debugging an install alone at 2 a.m. is the least productive form of learning available to you, and
there is a great deal of real work waiting.
