## Lecture

### 1. What a middleware is for

A robot is not one program. It is a camera driver, a LiDAR driver, a localiser, a planner, a
controller, and a safety monitor — written by different people, in different languages, running at
different rates, often on different machines.

Middleware is what lets those parts be written independently and still work together. ROS 2 gives
you:

- **Named, typed channels** (topics) instead of ad-hoc sockets
- **Discovery** — processes find each other without being told where anything is
- **Introspection** — you can list, inspect, record, and replay everything at runtime
- **Language independence** — Python and C++ nodes in one graph

The cost, which this course will make you feel repeatedly: the coupling that used to be a compile
error is now a **runtime** condition. Names, types, QoS, and domains must all agree, and when they
disagree, mostly nothing happens and nothing complains.

### 2. Drive-by-wire

MRider is a 12 V ride-on car whose mechanical steering and throttle are being replaced by
**electrically commanded** equivalents. Steering becomes a gearmotor plus an absolute angle sensor
closing a position loop; the throttle becomes a motor driver taking a signed command.

Three properties follow, and they shape everything:

1. **Actuation is a physical process with limits.** ±22.5° of steering. A rate limit. A stall
   current. Software cannot wish these away.
2. **Feedback is measured, not known.** Every number the autonomy sees came from a sensor with noise,
   latency, and blind spots.
3. **A human must always be able to take it back.** Not as a feature — as an architectural
   requirement that outranks everything else.

### 3. Command and feedback paths

```
joystick ──▶ /cmd_vel_joy ──┐
                            ├──▶ twist_mux ──▶ ackermann_steering_controller ──▶ wheels
navigation ──▶ /cmd_vel ────┘      (arbitrates)         (kinematics)

wheels ──▶ encoders ──▶ odometry ──┐
                                   ├──▶ EKF ──▶ /odom → base_link ──▶ SLAM ──▶ map
IMU ───────────────────────────────┘
```

`twist_mux` gives the joystick priority 100 and navigation priority 10. A human at the sticks wins.

!!! danger "But `twist_mux` is not the safety system"

    Read the comment at the top of `mitt_control/config/twist_mux.yaml`. It says so explicitly, and
    the honesty is the point.

    Real authority on this vehicle is **electrical and layered**: a hardware E-stop, a relay MUX that
    reverts to stock mechanical steering, a hardware RC signal MUX, and SBUS override. **Three of
    those four work with the software completely dead.** A software mux cannot do that job, and
    presenting it as though it could would be worse than having nothing — because people would trust
    it.

    This distinction — between what a component *does* and what it must never be *relied on* for —
    is one of the things this course is really about.

### 4. Rates are contracts, not preferences

Numbers you will meet today and keep meeting:

| | |
|---|---|
| `update_rate: 100` | Controller manager, so it is never the bottleneck |
| `reference_timeout: 0.5` | A command older than half a second is not a command |
| ≥ 50 Hz | Required rate for DBW status from the vehicle |
| ≤ 100 ms p95 | Joystick-to-wheel latency budget |

A system that meets its functional spec and misses its timing spec is broken. On a vehicle, it is
dangerous.

### 5. The shape of ROS 2 failure

Today's lab ends by breaking the system on purpose, and it will not be the last time. The pattern is
worth naming in week one:

> When something is **invisible rather than broken**, suspect the environment before you suspect your
> code.

Mismatched `ROS_DOMAIN_ID`, mismatched QoS, mismatched middleware — all produce silence, exit code 0,
and empty logs. Weeks 3 and 4 add two more members to this family.
