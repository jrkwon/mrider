## ★ Merge 3 — the ADR-SW4 gate

**The claim:** *`mitt_hardware` talks to the real Teensy, and the identical teleop launch runs in
simulation and on hardware, differing only in the plugin.*

This is the property the whole twin exists to support
([ADR-SW4](../../design/software.md)). Without it the twin is a demonstration. With it, the twin is
a test rig for the vehicle.

### What must be shown

| | |
|---|---|
| `mitt_hardware` loads and activates | `ros2 control list_controllers` on the vehicle: the Ackermann controller and `joint_state_broadcaster` both `active` |
| Same launch, two targets | `real.launch.py vehicle:=<n>` and `sim.launch.py vehicle:=<n>` bring up the same controllers, `twist_mux` and topics. **Show the difference between them, and that it is the plugin** |
| Status rate | `ros2 topic hz /mitt/dbw/status` at **≥ 50 Hz**, the number on screen |
| Teleop, wheels off the ground | A joystick command steers and turns the drive wheels |
| Both override layers | RC takes the vehicle back from the laptop. E-stop cuts traction and reverts to STOCK |
| Bring-up stage | Which [stage](../../design/safety.md#6-bring-up-protocol-staged-wheels-off-first) your vehicle has passed, with the evidence for it |

> [!CAUTION]
> **Wheels off the ground unless Stage 4 has passed**
>
> Bench before vehicle, wheels-off before wheels-on, walking pace before anything faster. A team
> that has not passed Stage 4 shows Merge 3 on stands, and that is a complete demonstration.
>
> Driving on the floor is [Stage 5](../../design/safety.md#6-bring-up-protocol-staged-wheels-off-first)
> and follows [build step 7](../../build/07-manual-drive.md): roles assigned, abort criteria read
> aloud, RC first. **A skipped stage is not a lost point. It is no demo on 12/21.**

A row that does not pass is shown as it is, with the reason and the evidence for the reason. That
is worth more than a row that passed once and cannot be repeated.

## Lecture

### 1. What is allowed to differ

The twin and the vehicle run the same launch structure. Four things differ, and each one is
deliberate:

| | Twin | Vehicle |
|---|---|---|
| Hardware plugin | `gz_ros2_control` | `mitt_hardware` |
| Clock | `use_sim_time:=true` | `use_sim_time:=false`, the laptop's wall clock |
| ROS domain | 0, with `ROS_LOCALHOST_ONLY=1` | **10 + N**, set by `MITT_VEHICLE=<n> source ros2_ws/setup_env.sh` |
| Sensor data | Gazebo bridges | RPLIDAR and camera drivers, and the Teensy through the micro-ROS agent |

Everything else is supposed to be identical: controllers, `twist_mux`, EKF, SLAM and Nav2
configuration, topic names and frames. **When something behaves differently on the vehicle, the
first question is which of those four rows it is, and the second is what else differs that should
not.**

> [!WARNING]
> **`use_sim_time` on the vehicle fails without an error**
>
> Every Nav2, SLAM and localization launch in this repository defaults to `use_sim_time:=true`,
> because the twin is where they were written. On the vehicle nothing publishes `/clock`, so a node
> left on simulated time sits at time zero: transforms are "too old", costmaps stay empty, and no
> log line says why.
>
> Pass `use_sim_time:=false` to **every** launch on the vehicle
> ([build step 8](../../build/08-autonomous.md)), and check one node:
> `ros2 param get /controller_server use_sim_time`.

### 2. The vehicle number, in three places

`vehicle:=<n>` selects your measured geometry, and the same number selects your ROS domain. It has
to agree in three places:

```bash
MITT_VEHICLE=2 source ros2_ws/setup_env.sh          # every terminal: domain 12
ros2 launch mitt_bringup real.launch.py vehicle:=2  # the body and the controller
ros2 launch mitt_navigation nav2.launch.py vehicle:=2 use_sim_time:=false
```

`real.launch.py` refuses to start in the wrong domain and says so. `nav2.launch.py` compares the
running robot with its own `vehicle:=` and prints a block headed `WRONG VEHICLE` when they differ.
Both checks exist because the failure they catch is otherwise silent: a planner sized for a
different car plans paths yours cannot follow.

The firmware names its own domain at build time
([software.md §3.4](../../design/software.md#34-ros-domain-one-per-vehicle)). That statement comes
from the micro-ROS client API and had not been confirmed on a vehicle when it was written. **Your
bring-up is where it is confirmed or corrected.**

### 3. Calibration is a file, with a date on it

| Subsystem | Artifact | Stale when |
|---|---|---|
| Steering zero and scale | `config/calibration/steering.yaml` | The sensor or the linkage was re-mounted |
| Drive odometry | `config/calibration/odom.yaml` | Tyres changed, or payload changed a lot |
| Camera intrinsics | `config/calibration/camera_front.yaml` | Lens refocused or camera replaced |
| Sensor extrinsics | The URDF joints, or `extrinsics.yaml` | The mast was moved, even slightly |
| Geometry | `config/vehicles/vehicle<n>.yaml` | Never, once measured, unless the chassis changes |

From [calibration.md §7](../../design/calibration.md#7-calibration-artifact-index): each artifact
carries the date, the operator, the vehicle and the git commit. The reason is the mast. It is the
part most likely to be bumped in a shared room, and **a LiDAR that has moved 3 cm produces a map
with doubled walls and no error message**, the failure you built on purpose in Lab 5.

### 4. Record the run, or it did not happen

A claim in the final report needs the number, the procedure, the raw data and the conditions
([grading](../grading.md#on-acceptance-evidence)). The raw data is a bag:

```bash
ros2 bag record -o merge3_teleop /mitt/dbw/status /mitt/dbw/command /cmd_vel /tf /tf_static /scan
```

Write down, with every bag: the git commit of your fork, the firmware commit, the vehicle number,
the battery voltage at the start, and who was operating. Copy bags off the laptop before it leaves
the room.

> [!TIP]
> **Record the failures too**
>
> A bag of the run that went wrong is the evidence your failure analysis is graded on. Teams lose
> it by re-running "one more time" before saving anything.
