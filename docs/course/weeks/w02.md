## Lecture

### 1. Workspaces, packages, `colcon`

```
ros2_ws/
├── src/            your packages, and cloned upstream sources
├── build/          intermediate build artifacts
├── install/        what you actually source
└── log/            build and test logs
```

`colcon build` walks `src/`, resolves the dependency order from each `package.xml`, and installs into
`install/`. Sourcing `install/setup.bash` puts those packages on your path.

**Two build types matter here.** `ament_cmake` for C++ and for packages that mainly install files;
`ament_python` for pure-Python nodes.

!!! info "Every MITT package today is `ament_cmake` and contains zero nodes"

    Look at `ros2_ws/src/`. Seven packages: launch files, YAML, URDF, message definitions, a world.
    **Not one C++ or Python node in the entire workspace.**

    That is not an oversight — it is where the project currently is. The nodes that should exist
    (`mitt_hardware`, the odometry node, `mitt_bench`, perception) are exactly what the four tracks
    build from Week 6. You are about to write the first node in this repository.

`--symlink-install` links rather than copies, so editing a Python file takes effect without
rebuilding. Use it; it will save you hours.

### 2. Publishers, subscribers, and the timer

The rhythm of almost every ROS 2 node:

```python
class Thing(Node):
    def __init__(self):
        super().__init__('thing')
        self.pub = self.create_publisher(Msg, '/out', 10)
        self.create_subscription(Msg, '/in', self.on_in, 10)
        self.create_timer(0.1, self.tick)     # 10 Hz
```

The `10` is the **queue depth**: how many messages to buffer if the other side is slow. It is part of
the QoS profile, which Week 3 opens up properly.

**Callbacks must not block.** A callback that sleeps, or does heavy computation, stalls every other
callback in that executor. Symptoms look like a performance problem, not a structural one.

### 3. Choosing a rate

Not a matter of taste. It is bounded from below by the consumer's timeout and from above by what the
producer and network can sustain.

For MRider's command stream:

| | |
|---|---|
| `reference_timeout: 0.5 s` | The controller zeroes after this. So **> 2 Hz**, absolute floor |
| Controller runs at 100 Hz | Publishing faster than this buys nothing |
| ≤ 100 ms p95 latency budget | Argues for ≥ 20 Hz so a dropped message does not blow the budget |

10–20 Hz is the sensible band. Lab 2 has you publish at 10 Hz, then at 1 Hz to watch the floor
enforce itself.

### 4. Ackermann kinematics, informally

The formal treatment is [Week 5](../labs/lab5.md). What you need today:

$$ \omega = \frac{v \tan\delta}{L} $$

Yaw rate is **proportional to forward speed**. At `v = 0`, ω is zero regardless of steering angle. A
car cannot pirouette.

This is why your square driver keeps `linear.x` non-zero through its turns, and it is why the
navigation stack later needs a planner that can plan *reversing manoeuvres* — because for this
vehicle, "turn around" is not a primitive.

### 5. Where odometry comes from — and what it cannot see

Your node subscribes to `/ackermann_steering_controller/odometry` and reads a position. That number
is integrated from wheel rotation and steering angle through the kinematic model above.

On the **real** vehicle, the measurement chain is narrower than you might assume:

- Both rear motors are wired **in parallel to a single driver channel**
- Only **one** of them carries an encoder ([ADR C](../../design/dbw.md))
- So the measurement is taken at one motor shaft

What that shaft cannot observe: gearbox backlash downstream of it, tyre slip and deformation, and the
fact that in a turn the two rear wheels travel **different distances** — of which it sees one.

!!! quote "Which is why odometry is fused, not trusted"

    This is the argument for the EKF in Week 6. It is not a formality bolted on because textbooks
    have one; it is a response to a specific, documented, deliberately accepted measurement gap.

    There is a diagram of the whole chain in [M5](../../learn/m5-slam.md), including a note that the
    encoder's pulses-per-revolution is itself **unverified** — a predecessor project's firmware and
    its own bill of materials disagree by a factor of three, and the design record explicitly forbids
    inheriting either number.
