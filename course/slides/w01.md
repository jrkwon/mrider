# 1. What middleware is for

---

# A robot is not one program

- Camera driver · LiDAR driver · localiser · planner · controller · safety monitor
- Different authors, different languages, different rates, sometimes different machines

**ROS 2 gives you:**

- Named, typed channels instead of ad-hoc sockets
- Discovery — processes find each other unaided
- Introspection — list, inspect, record, replay at runtime
- Python and C++ in one graph

---

# What it costs you

Coupling that used to be a **compile error**
is now a **runtime condition.**

- Topic names must agree
- Message types must agree
- QoS profiles must agree
- Domain IDs must agree

When they disagree, mostly **nothing happens, and nothing complains.**

# 2. Drive-by-wire

---

# Replacing the driver

Mechanical steering and throttle become **electrically commanded** equivalents.

- Steering → gearmotor + absolute angle sensor closing a position loop
- Throttle → motor driver taking a signed command

Three consequences follow, and they shape everything.

---

# Three consequences

1. **Actuation is physical, and has limits**
   ±22.5° of steering. A rate limit. A stall current. Software cannot wish these away.

2. **Feedback is measured, not known**
   Every number the autonomy sees came from a sensor with noise, latency, and blind spots.

3. **A human must always be able to take it back**
   Not a feature — an architectural requirement outranking everything else.

---

# The command path

```
joystick ──▶ /cmd_vel_joy ──┐
                            ├─▶ twist_mux ─▶ ackermann_steering_controller ─▶ wheels
navigation ─▶ /cmd_vel ─────┘   (arbitrates)          (kinematics)
```

`twist_mux` priorities: **joystick 100**, navigation 10.

A human at the sticks wins.

---

# The feedback path

```
wheels ─▶ encoder ─▶ odometry ──┐
                                ├─▶ EKF ─▶ odom→base_link ─▶ SLAM ─▶ map
IMU ────────────────────────────┘
```

- One encoder, on one motor shaft, of two motors wired in parallel
- Cannot see: gearbox backlash · tyre slip · the other wheel

**Which is why it gets fused rather than trusted.** (Week 6)

---

<!-- _class: quote -->

> `twist_mux` is not the safety system.

And the design documents say so out loud.

---

# Real authority is electrical

| Layer | Works if the firmware has crashed? |
|---|---|
| Hardware E-stop — cuts traction | **Yes** |
| Relay MUX — reverts to stock steering | **Yes** |
| Hardware RC signal MUX | **Yes** |
| SBUS override into the controller | No |

A software mux dies with the software it was meant to protect you from.

---

# The principle

A safety mechanism that shares a failure mode
with the thing it protects against
**is not a safety mechanism.**

Software presenting itself as a safety system, then failing silently,
is worse than nothing — because people trust it.

# 3. Rates are contracts

---

# Numbers you will keep meeting

| Value | Meaning |
|---|---|
| `update_rate: 100` | Controller manager, so it is never the bottleneck |
| `reference_timeout: 0.5` | A command older than 0.5 s is not a command |
| ≥ 50 Hz | Required DBW status rate from the vehicle |
| ≤ 100 ms p95 | Joystick-to-wheel latency budget |

A system that meets its functional spec and misses its timing spec is **broken**.
On a vehicle, it is dangerous.

# 4. How ROS 2 fails

---

# It fails by going quiet

Today you will deliberately mismatch `ROS_DOMAIN_ID` and observe:

- 2 topics instead of 21
- **Exit code 0**
- **Zero bytes on stderr**
- Nothing in any log

The simulator is running perfectly the whole time.

---

# The habit to build now

> When something is **invisible** rather than **broken**,
> suspect the environment before you suspect your code.

- A crash hands you a stack trace and a line number
- This hands you nothing — which is exactly what makes it expensive

Weeks 3 and 4 add two more members to this family.
