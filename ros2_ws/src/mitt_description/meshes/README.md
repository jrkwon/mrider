# MITT meshes

## `mitt_body.obj` — vehicle body shell

**Provenance.** Derived from the **"SUV"** model by **Open Robotics** on Gazebo Fuel,
<https://app.gazebosim.org/OpenRobotics/fuel/models/SUV>, released under
**CC0 1.0 Universal** (public domain dedication). CC0 requires no attribution; it is
recorded anyway, and it is why this model was chosen over better-looking alternatives with
`NonCommercial` or `NoDerivatives` terms — the same reasoning that picked the Depot world
(see `mitt_sim/worlds/depot.sdf`).

**Why this model.** The source is a Hummer H2: boxy, upright, flat-roofed, with squared
wheel arches. The MITT donor vehicle is a Land Rover Defender–style 12 V ride-on, which has
the same silhouette. Body proportions are L : W : H = 1 : 0.52 : 0.37 against the donor's
1 : 0.57 : 0.48, so it scales down without looking stretched.

**It is a visual proxy, not a scan.** It is not the donor vehicle, and no dimension in the
project is derived from it. All geometry still comes from `config/mitt_dimensions.yaml`.

### What was changed, and why

Regenerate with:

```bash
python3 scripts/extract_body.py <fuel-cache>/suv/4/meshes/suv.obj meshes/mitt_body.obj
```

1. **Wheels removed.** The source carries `Wheel_Front_Left`, `Wheel_Front_Right` and
   `Wheel_Rear` groups. MITT's URDF has its own four wheel links that steer and roll; baked-in
   wheels would double-render and sit frozen while the real ones turned.

2. **The upstream −90° Z rotation is baked in** so +X is forward (ROS convention). This has to
   be baked rather than left to the URDF `<origin rpy>`: URDF applies `<scale>` in the *mesh*
   frame, before the origin transform, so with a rotation still pending a non-uniform
   `scale` on X would stretch the vehicle's **width** instead of its length. Baking removes
   that trap.

3. **Normalised to a unit bounding box** — span 1.0 per axis, centred on X/Y, resting on
   Z = 0. This is the useful part: the URDF `<scale>` is then literally the vehicle's size in
   metres, fed straight from `mitt_dimensions.yaml`. The mesh keeps tracking those numbers
   when they are finally *measured*, with no geometric literals anywhere.

### Texture — generated, not photographic

The body carries `mitt_body_texture.png`, generated by
`scripts/make_body_texture.py` from the mesh's own geometry. Every texel is
classified by barycentric interpolation of the surface point that owns it —
height, surface normal, position — so the paint registers with the body by
construction rather than by eye. Roof, greenhouse glass, body paint, lower trim,
and head/tail lamps each get a flat colour. The whole map is **7.5 kB**.

Regenerate with:

```bash
python3 scripts/make_body_texture.py meshes/mitt_body.obj meshes/mitt_body_texture.png
```

**Why generated rather than the upstream texture.** The Fuel model ships a
736 kB photographic skin, but it is a photographic **Hummer H2** — grille,
badges, chrome — and this mesh only stands in for a Defender-style 12 V ride-on.
Painting one real vehicle's bodywork onto a proxy for a different vehicle
asserts something untrue about the platform, which is the one habit this project
works hardest to avoid.

**Why the lamps are worth the trouble.** They are the only feature that makes
the vehicle's heading readable at a glance. In RViz, with TF axes off, a
uniformly coloured shell gives a student no way to tell which end is the front —
and that question comes up in every TF, odometry and Nav2 lab.

#### Correction (2026-09-04) — the previous claim here was wrong

This section used to say:

> It was tried both beside the mesh and under `materials/textures/` (the gz
> convention), and **rendered in neither**: gz-sim loads the mesh without any
> warning and simply draws it untextured.

**That is not true, and it was recorded as a fact about the renderer.** gz-sim
Harmonic renders mesh textures here without difficulty. The counter-example was
running the whole time: the **Depot world** — the warehouse the vehicle drives
around every session — is a Fuel model whose `Depot.dae` references
`../materials/textures/WALLS_Albedo.png` and friends by exactly the same
relative-path convention, and it draws fully textured.

What actually suppressed the texture was **our own description**:

| | |
|---|---|
| `mitt_base.xacro` | `<material name="mitt_white"/>` sat on the mesh visual. URDF→SDF conversion turns that into an SDF `<material>` whose diffuse colour **overrides the mesh's own** |
| `mitt_base.xacro` | `<gazebo reference="chassis_link"><material>Gazebo/White</material></gazebo>` — Gazebo **Classic** script syntax, inert in Harmonic |

So the shell was being painted white by MITT, not left untextured by Gazebo. The
texture files had been installed correctly both times; two dangling symlinks
were still sitting in `install/` from those attempts, pointing at both of the
locations the note above claimed had failed.

The lesson is the one this project keeps relearning and writing down: **a
symptom is not a diagnosis.** "The tool cannot do X" is a strong claim, and it
needs a control — here, any other textured model in the same scene would have
falsified it in a minute.

### Known simplification: pillars read as glass

A- and B-pillars sit inside the greenhouse height band and are painted **as
glass**, because the classifier separates surfaces by height and normal rather
than by UV island. At the scale this vehicle is viewed the band still reads
correctly as a greenhouse, and fixing it properly would mean island-level
analysis for a cosmetic gain on a proxy mesh. Written down rather than left to
be discovered.

### Renderer difference: RViz uses one material per link

Verified 2026-09-04, worth knowing before it is mistaken for a bug.

**Gazebo** paints every `<visual>` with its own material. **RViz2's RobotModel
display renders the geometry of every visual but applies a single material per
link**, taken from the first one. So the wheel rim, the LiDAR cap and the
camera lens are all correctly *shaped* in RViz and all wear their link's base
colour.

The body texture is unaffected — `chassis_link` has exactly one visual, so its
MTL applies in both.

This is left alone on purpose. Fixing it means a child link per accent, joined
by a fixed joint, which would add half a dozen decorative frames to a TF tree
that students are asked to read in the Week 5 lab. Cosmetics do not get to
pollute the frame graph.

### Collision is still a box

The mesh is used for **visual only**. Collision and inertia remain the primitive
box in `mitt_base.xacro`. Mesh collision would cost physics time for no benefit
— and worse, it would silently change the vehicle's collision envelope whenever
the mesh was swapped, decoupling physics from the documented dimensions.
